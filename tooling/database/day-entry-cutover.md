# 支出履歴の切り替え手順

この手順は、旧版の支出を保持したまま、履歴の順序と保存キーを新版へ切り替えるためのものです。旧版と新版を同じDBに向けて通常稼働させる段階はありません。メンテナンス中は支出と履歴の更新を停止します。

## 適用前

1. 対象の Worker、ルート、バージョン配分、D1 名と UUID、移行履歴を確認します。同じ DB に書く別の Worker、バージョン URL、定期処理、手動ツールも棚卸しし、復旧点を確保します。
2. 更新受付を止め、実行中の旧リクエストを終了させます。前回のレビュー用ビルド（`ad0be6e`）が書いた DB は、この手順の対象外です。正の `write_order` や旧 receipts が見つかると移行は停止します。履歴編集だけを実行した痕跡はこれらの列に残らないため、当該ビルドが書いていないことは配備記録でも確認してください。
3. 読み取り専用の診断を同じ対象に対して実行し、結果が空であることを確認します。従来スキーマには `--legacy-schema` を使います。前段の `day_entry_receipts_and_order` を適用済みならフラグを外します。

   ```bash
   # TARGET_D1 と TARGET_ENV には確認したDB名と環境を指定する。
   cutover_sql=$(node scripts/day-entry-cutover-diagnostics.ts --legacy-schema) &&
     pnpm wrangler d1 execute "$TARGET_D1" --env "$TARGET_ENV" --remote --command "$cutover_sql" --json
   ```

   コマンドが成功し、出力された JSON 配列に `success: true` と空の `results` (`[]`) を持つ結果が1件あることを確認してから進みます。Wrangler 4.162.0 では `--remote --file` はインポート経由で実行されるため、診断の SELECT は上記の `--command` で実行します。[Wrangler の実行オプション](https://developers.cloudflare.com/workers/wrangler/commands/d1/#d1-execute)

   `results` に行がある場合は `budget_period_id`、`date`、`issue` を確認し、対応するバックアップや書き込み記録と照合します。順序を裏付ける証拠が得られるまで受付停止を継続してください。診断は元の行や日計を書き換えません。証拠で順序を確定できても診断が解消しない場合は、証拠を反映した修復手順を別途レビューしてください。順序候補が複数ある場合、金額と一致しない場合、履歴のない日計、または時刻の逆転がある513件以上の日は移行が停止します。

## 適用と再開

1. 対象環境の既定の移行手順で未適用の SQL を適用します。最後の移行は一つのトランザクションで順序を再検証し、履歴と receipts のテーブル名を切り替え、この DB 専用の epoch を登録します。検証に失敗すると最終移行はロールバックされます。先に成功した移行は適用済みのままです。[Wrangler の移行仕様](https://developers.cloudflare.com/workers/wrangler/commands/d1/#d1-migrations-apply)
2. 最終移行が記録され、旧テーブル名が存在せず、`day_entry_cutover` に epoch が1件あることを確認します。その後に新版のみを配備します。旧版へ流入しても、旧テーブルに対する支出書き込みと履歴編集は D1 で失敗します。旧版への流入排除は、旧画面を返さずサービスを復旧するためにも必要です。
3. 新版の `GET /api/periods` が返す `Day-Entry-Epoch` を確認します。隔離した検証環境では同じ現在キーによる同一リクエストの再送が1件だけ計上されることを確認し、旧キーとキーなしの保存が HTTP 412 になることを確認します。切り替えをまたぐ不明な保存は、履歴確認の前に新しいキーへ置き換えて再送しないでください。
4. 対象の新版だけがルーティングされ、古い画面のキャッシュからの配信が解消してから受付を再開します。最終移行後に旧版へ戻すと支出書き込みが失敗します。受付再開後は新しい書き込みを保全し、切り替え後のスキーマに対応する修正版で復旧します。

旧版の API に epoch より前に送られたキーは、元の保存が確定したか判別できません。新版で新たに用いるキーは、切り替え後に取得した epoch と、その保存ごとの乱数をドットで連結したものです。DB の切り替え時や障害時に旧キーを新版のキーへ自動変換しないでください。
